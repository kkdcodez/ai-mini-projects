# 001. 데이터 분석 및 전처리

**프로젝트:** 공유자전거 대여 수요 예측 (회귀)  
**작성 범위:** CP-01~CP-03  
**근거:** `code/01_regression_bike_demand_completion.ipynb`의 실행 결과

> **작성 예시:** 이 문서는 **무엇을 확인했는지(결과) → 무엇을 알게 되었는지(해석)**를 기록합니다. 입력 특성의 최종 **선택 이유**는 `adr.md`에 따로 정리합니다.

## 1. 데이터 탐색 (CP-01)

- **데이터 크기:** 17,379행, 17열 (`hour.csv`; 한 행은 특정 날짜·시간의 대여 기록)
- **결측값 및 중복 행:** 전 열 결측값 0개, 중복 행 0개
- **대여량(`cnt`) 분포의 특징:** 평균 189.46대, 중앙값 142대, 최소 1대, 최대 977대. 적은 대여량에 관측치가 몰리고 큰 값 쪽으로 꼬리가 길다.
- **평균 대여량이 높은 시간대:** 17시 461.5대, 18시 425.5대, 8시 359.0대 (가장 낮은 시간대: 4시 6.4대)

**분석:** 대여량은 오전 8시와 오후 17~18시에 집중되는 출퇴근 시간대 패턴을 보인다. 수요가 높은 시간과 낮은 시간의 차이가 크므로, 모델의 시간대별 예측 오류를 별도로 확인할 필요가 있다.

## 2. 데이터 분할 및 누수 확인 (CP-02)

- **Train:** 2011-01-01 ~ 2012-05-25 / **12,139건** (511일) / `cnt` 평균 **약 159.7대**
- **Validation:** 2012-05-26 ~ 2012-09-11 / **2,616건** (109일) / `cnt` 평균 **약 281.0대**
- **Test:** 2012-09-12 ~ 2012-12-31 / **2,624건** (111일) / `cnt` 평균 **약 235.8대**
- **시간 순서로 분할한 이유:** 미래 수요를 예측하는 상황을 반영하기 위해 날짜별로 순서대로 70% / 15% / 15% 수준으로 분할했다. 같은 날짜의 기록이 서로 다른 집합에 섞이지 않도록 했다.
- **`casual + registered == cnt` 확인 결과:** 전체 **17,379행 모두 `True`**
- **누수 가능성이 있어 제외한 특성과 이유:** `casual`, `registered`는 총 대여량 `cnt`를 구성하는 대여 후 집계값으로, 예측 시점에 알 수 없어 제외했다. (`cnt`는 정답 열로 입력에서 제외)

**분석:** Validation 평균 대여량(281.0대)이 Train(159.7대)보다 크게 높아, 두 집합의 수요 수준이 다르다. 이후 Train과 Validation의 오차 차이를 해석할 때 모델의 과대적합뿐 아니라 이 분포 차이도 고려해야 한다.

## 3. 상관관계 및 입력 특성 분석 (CP-02)

> 아래 상관계수는 **Train 데이터**에서 계산한 값이다.

- **`temp`와 `cnt`의 상관관계:** **+0.398** (양의 선형 관계)
- **`hum`과 `cnt`의 상관관계:** **−0.301** (음의 선형 관계)
- **`windspeed`와 `cnt`의 상관관계:** **+0.094** (약한 선형 관계)
- **`temp`와 `atemp`의 상관관계:** **+0.992** (두 입력 특성 사이에 매우 높은 상관)
- **사용한 특성 목록(`FEATURES`):** `season`, `yr`, `mnth`, `hr`, `holiday`, `weekday`, `workingday`, `weathersit`, `temp`, `hum`, `windspeed` (**11개**; CP-03에서 `is_commute_hour`를 더해 **12개**)

**분석:** `temp`는 대여량과 양의 관계, `hum`은 음의 관계가 관찰되었다. 반면 상관계수는 **선형 관계**를 보여주므로, `windspeed`의 값이 작다는 이유만으로 트리 모델에서의 유용성까지 단정할 수 없으며, `casual`처럼 누수가 있는 특성은 상관이 높아도 사용할 수 없다.

## 4. 특성공학 및 전처리 (CP-03)

- **생성한 특성:** `is_commute_hour`
- **특성 생성 조건:** `workingday == 1`이고 `hr`이 **7·8·9·17·18·19** 중 하나이면 1, 아니면 0 (Train에서 1의 비율 **0.173**)
- **범주형 특성 처리:** `season`, `mnth`, `hr`, `weekday`, `weathersit`에 **OneHotEncoder** 적용 (`handle_unknown='ignore'`; 변환 후 **51열**)
- **수치형 특성 처리:** `temp`, `hum`, `windspeed`에 **StandardScaler** 적용 (Train 기준 평균·표준편차 사용; **3열**)
- **이진 특성 처리:** `yr`, `holiday`, `workingday`, `is_commute_hour`는 **그대로 전달** (`passthrough`; **4열**)
- **Train 전처리 전후 Shape:** **(12,139, 12) → (12,139, 58)**
- **Validation에 적용한 변환 기준:** **Train만으로 `fit`**한 One-Hot 범주와 표준화 기준을 Validation에 `transform`으로 적용했다. Validation Shape: **(2,616, 12) → (2,616, 58)**.

## 5. 데이터 분석 요약

**모델 학습 전에 확인한 중요한 점 1~2가지:** ① `casual`·`registered`는 정답의 구성 요소이므로 반드시 제외하고, `temp`와 정보가 중복되는 `atemp`도 제외했다. ② 출퇴근 시간대의 대여량이 특히 높고 Train·Validation 간 평균 수요도 달라, 시간대별 오류와 분할 간 성능 차이를 함께 분석해야 한다.

> 입력 특성에 대한 **최종 선택과 근거**는 `adr.md`의 **의사결정 ①**에 작성한다.
